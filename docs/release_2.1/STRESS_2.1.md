# Стресс-тест 2.1: основной сканер с выключенной и включённой аналитикой

Скрипт `scripts/stress_sqlite.py` (тот же, что для 2.0.1). Условия:
- 180 с, реальные потоки и соединения SQLite;
- 801 токен, 20 001 событие эмиссии, 7 000 наблюдений;
- ответы источников подменены и приходят с задержкой 20–150 мс;
- три потока пользователя работают через веб-API;
- без инъекции сбоев записи.

Режимы аналитики:
- **обычный режим** (`--analytics-realistic`): оба модуля включены с настройками по умолчанию — интервалы 60 и 30 мин,
  пересчёт только при изменении данных, откладывание при перегрузке;
- **наихудший случай** (`--analytics`): каждую секунду ставится принудительный пересчёт всех токенов. Из интерфейса так сделать нельзя:
  повторное нажатие «Пересчитать» не создаёт новых заданий, пока прежнее не выполнено.

## Выводы
- **Обычный режим не отличается от выключенной аналитики** в пределах разброса между запусками:
  - котировок 312 (без аналитики 301–305), обнаружения и анализа 168 (164–169);
  - задержки пользовательских действий те же;
  - аналитика выполнила первый расчёт, а при загруженных основных очередях (221 задача) откладывалась 10 раз — так и задумано.
- **Наихудший случай** — непрерывный принудительный пересчёт, недостижимый из интерфейса:
  - котировок 296 (−2–3%, в пределах разброса);
  - обнаружения и анализа 149 (−10%);
  - p95 чтения списков и карточки примерно вдвое выше (626 мс против 247–355), медианы почти те же.
  Остаточное влияние есть, и оно приведено как есть.
- **Сеть.** Во всех режимах аналитика не сделала ни одного запроса к источникам (`из очереди аналитики = 0`).
- **Надёжность.** Во всех режимах:
  - 0 необработанных исключений и 0 ошибок задач;
  - все очереди живы;
  - `integrity_check = ok`;
  - 0 потерянных, дублированных и непомеченных событий;
  - ни одной транзакции дольше 1 с.

## Как к этому пришли (честно)
Первая версия 2.1 без ограничения доли времени в наихудшем случае заметно мешала сканеру, хотя ошибок не было.
Python исполняет потоки по очереди (GIL), и непрерывный расчёт отнимал у них время:

| Версия аналитики | Котировок | Обнаружения и анализа | p95 чтения карточки, мс | p95 ожидания записи, мс |
|---|---|---|---|---|
| выключена (два запуска) | 301 / 305 | 169 / 164 | 355 / 247 | 45 / 42 |
| без ограничения | 237 (−21%) | 103 (−39%) | 1016 | 747 |
| пауза 3× | 273 (−9%) | 139 (−18%) | 620 | 113 |
| **пауза 6× (итог)** | **296** | **149** | **626** | **143** |
| пауза 6×, обычный режим | 312 | 168 | 237 | 90 |

Отсюда настройка `analytics.pause_ratio = 6`: после расчёта каждого токена очередь делает паузу в 6 раз дольше расчёта, и аналитика
получает не больше ≈ 14% времени. Это проверяет регрессионный тест `test_analytics_cpu_share_is_limited`.
Полный проход по рабочей базе (171 + 2 токена) с этой паузой — около 3 с. Сырые отчёты лежат в `docs/release_2.1/stress/`.
